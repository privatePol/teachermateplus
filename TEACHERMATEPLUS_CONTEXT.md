# TEACHERMATEPLUS_CONTEXT.md

## 1. What TeacherMate+ Is
TeacherMate+ V1 is a multi-tenant, multi-campus academic grading and governance platform designed to centralize class grading workflows and reduce operational risk from disconnected grade files.

## 2. Current Operating Modules

### Faculty Question CSV String Sanitation
- Departmental Exam CSV parsing sanitizes only the already parsed `question_text` and Choices A-D before the shared `QuestionPayloadService` validation boundary. It expands TABs with four-column tab stops; normalizes CRLF/CR, vertical tab, and form feed to LF; converts NBSP to an ordinary space; and removes zero-width spaces and embedded BOMs. It does not preprocess raw CSV syntax, headers, `correct_answer`, or `difficulty`.
- The sanitized payload is fingerprinted, persisted in `QuestionImportRow`, previewed, and reused unchanged by resumable confirmation. Existing stored question text is sanitized only in a comparison copy for duplicate detection; no Question record or stored fingerprint is rewritten. The file SHA-256 remains a digest of the original uploaded bytes.
- Repeated ordinary spaces, table-style alignment, meaningful/blank LF lines, academic Unicode, ZWNJ, and ZWJ remain unchanged apart from the existing leading/trailing trim. The shared validator still rejects NUL, remaining prohibited C0/C1 controls, DEL, surrogates, Arabic Letter Mark, LRM/RLM, bidi embeddings/overrides/PDF/isolates, and any unsupported artifact outside the explicit CSV sanitation list. A changed row receives one generic non-blocking preview warning without exposing question content or code-point details. No migration or retrospective cleanup is required.

### Automatic Generation Readiness Report
- Contributor roster source evidence uses one canonical effective snapshot scope: assignment tenant/campus when present, with the approved linked-offering fallback for legacy assignments whose assignment scope is `(NULL, NULL)`. Synchronization, OPEN readiness comparison, and the live close-time evidence hash share that helper. This keeps an unchanged legacy-null Draft roster current without weakening live eligibility or true stale detection. Submitted contributions retain frozen attribution, and Closed courses continue to evaluate only their persisted frozen roster boundary.
- Included rows distinguish roster state operationally on both screen and print. A roster without `contributor_roster_initialized_at` says `Contributor roster has not been initialized.` and directs the manager to Initialize. An initialized roster whose eligible Faculty evidence changed says `Contributor roster needs synchronization because the eligible faculty list has changed.` and directs the manager to Synchronize. The former is never labeled stale or given a Synchronize instruction.
- Admin Portal Contributor Completion Monitoring links to a separate GET-only `Automatic Generation Readiness` report and printer-friendly view. The report is restricted to Automatic Generation cycles and strongly bounds evaluation to one authorized cycle, with optional Period and Course filters. Missing cycle input defaults to the newest authorized Automatic cycle; malformed, stale, cross-tenant, or unauthorized allowlisted values return zero rows and are preserved through the print URL so print cannot broaden the screen result.
- Included courses require existing `departmental_exams.manage_exam_generation` authority across every distinct participating Campus ID from `CycleCourseOffering`; Exempt visibility uses the separate status-independent Automatic inclusion-management map. Both retain active feature/user/role rules, GLOBAL/NULL grant support, tenant/campus scope, and direct-DENY precedence. No Manual configurator/reviewer authority, new permission, or menu item is introduced.
- Screen and print expose the same seven management columns only: No., Authorized Course, Campuses Offered, Final Exam Items, Contribution Progress, Automatic Exam Generation Status, and Action Needed. No. is sequential over the rendered authorized/filtered rows and restarts at 1 after filtering; Final Exam Items is a centered narrow column. Both views end with the same Report Summary: total rendered authorized courses plus Ready for Generation, Waiting for Deadline, Needs Questions, Faculty Incomplete, Blocked, Generated, and Exempt counts taken directly from the rows' existing final management statuses. The removed quota, Faculty Completion, campus-requirement, usable-total, and separate pool-readiness columns remain internal calculations where the single status or an action bullet needs them.
- Contribution Progress is monitoring only. The numerator counts saved questions belonging to Submitted `FacultyContribution` rows for the exact `CycleCourse`, without logical-fingerprint deduplication. The denominator uses the materialized effective `CourseExamConfiguration.questions_required_per_faculty` DEFAULT/OVERRIDE value multiplied by the number of distinct participating campus snapshots, so 60 across three campuses is 180 and no value is hardcoded to 50. Submitted campus names are deduplicated from participating frozen `source_campus` attribution; current assignment changes do not rewrite historical Submitted attribution.
- The internal pool assessment still uses the generator's Submitted-only validation, confirmed-import rule, normalized logical grouping, participating-campus policy, fixed 30/50/20 per-set difficulty allocation, and exact identity-aware Set A/B solver. Routine usable/unique/duplicate statistics are no longer displayed. Shortages produce concise action bullets such as `Add 6 usable Easy questions.`; invalid/unconfirmed rows remain genuine blockers. Ordinary `build_problem()` and `ExamGenerationService.generate()` behavior are unchanged.
- The single management status precedence is `EXEMPT`, `GENERATED`, genuine operational/configuration/roster `BLOCKED`, `FACULTY INCOMPLETE` for `REQUIRE_ALL`, technical `NEEDS QUESTIONS`, `WAITING FOR DEADLINE`, and `READY FOR GENERATION`. Current Faculty counts come from `ContributorRosterReadinessService.required_active_count`, `submitted_required_count`, and `incomplete_active_count` only when the roster is current. Historical Submitted contributors can still supply valid questions without counting toward current OPEN-roster completion.
- Under `AVAILABLE_WITH_WARNING`, a multi-campus course with a technically sufficient one-campus Submitted pool may reach `WAITING FOR DEADLINE` or `READY FOR GENERATION`; missing campuses appear only as concise bullets such as `No usable submitted questions from NCBA Fairview.` `STRICT` keeps missing representation blocking. Contributor Completion exposes the report only through the existing Included/Exempt Automatic authority maps with tenant, every-campus, GLOBAL/NULL, and direct-DENY semantics. Exempt rows remain minimal with Not applicable progress and `No generation required.`
- Cross-cycle authorization discovery loads only lightweight CycleCourse/Campus identity rows. The selected/default cycle and Course filter are validated before loading report objects; only then are that selected scope's configurations, Faculty contributions, offering snapshots, and current generated revisions prefetched. Invalid, stale, unauthorized, and cross-tenant cycle IDs evaluate no historical course pool and load no historical heavy relations.
- Screen and print share one report composer and one feasibility evaluation per visible Included course. Responses are private/no-store and aggregate-only: they contain no question text, choices, correct answers, normalized fingerprints, question/source IDs, GenerationProblem, or solver-state details. GET never calls `AutomaticExamDeadlineService`, generates sets, closes intake, changes roster/configuration/processing state, or writes an audit. Contributor Completion's existing printer-friendly four-column contract remains unchanged.

### Administrative Faculty Assignment Acceptance
- `AdministrativeFacultyAssignmentAcceptanceService` and the dry-run-default `administratively_accept_faculty_assignments` command provide a non-impersonating administrative path for official assignments. Tenant, Academic Year, Term, actor, and a non-empty reason are mandatory; Campus and `Course.exam_department` are optional narrowing dimensions. Execution additionally requires `--execute` and the exact approved `--expected-candidate-hash`; `--include-readiness-anomalies` is a separate deliberate override.
- Executable rows are active FacultyAssignment records in exact assignment/offering tenant-campus scope, attached to the requested active tenant/year/term and an active/open offering whose required hierarchy is active, with `response_status=PENDING`, null `responded_at`, `accepted_at`, and `accepted_by`. A non-null `Course.exam_department` must be active and tenant-consistent; null keeps the established policy. ACCEPTED, DECLINED, CLARIFICATION_REQUESTED, EXPIRED, inactive, malformed, inconsistent, closed, and out-of-scope rows are never overwritten. Account inactivity, unusable password, missing FACULTY membership, inactive UserRole membership, inactive linked FACULTY Role, and tenant/campus/offering-department role-scope mismatches are reported explicitly; they block execution unless deliberately overridden.
- Non-superuser actors require direct-DENY-aware `faculty_assignments.update` authority for every candidate. Exact applicable direct ALLOW is department-global within its tenant/campus because UserPermission has no department field; otherwise each ordinary offering department and non-null Exam Department must be covered by an active UserRole whose active Role itself carries the active permission. Scope from unrelated Roles never composes with the permission. Execution locks and re-fetches the requested tenant/year/term/actor and optional narrowing rows, all term-scoped offerings and assignments, their courses/sections/programs/campuses/departments, assigned faculty accounts, actor/FACULTY memberships and linked Roles, and applicable Permission/RolePermission/UserPermission rows before rebuilding eligibility, authorization, readiness, candidates, and hash. The SHA-256 fingerprint includes the Exam Department identity, tenant/campus, and active state plus every hierarchy state used by eligibility. Drift, malformed state, authorization exclusion, anomaly-gate failure, update failure, or audit failure leaves zero assignment/audit writes.
- A successful batch uses one timestamp and batch UUID, sets the complete accepted state, stores the actual administrative actor in `accepted_by`, and writes exactly one `ADMINISTRATIVE_FACULTY_ASSIGNMENT_ACCEPTANCE` audit per changed assignment with truthful before/after values, reason, actor, academic scope, assignment/offering IDs, and `source=management_command`. No HTTP/IP/user-agent provenance is fabricated. UI guidance describes Accepted as faculty acceptance or authorized administrative confirmation and never assumes `accepted_by == faculty_user`; no provenance field or migration is required. The Faculty endpoint, overdue expiration, Planning & Readiness definitions, and Departmental Exam contribution authorization remain unchanged. SQLite-backed focused and transaction-aware tests pass, but live/disposable MariaDB concurrency verification was unavailable; the independent C verdict therefore remains pending a separate read-only re-review. Nothing is staged, committed, pushed, deployed, or production-active.

### Stage 5 Question Content Character Safety
- `QuestionPayloadService.validate()` is the shared manual/CSV question-content boundary. It preserves ordinary Unicode academic text, spaces, punctuation, and supported line breaks; CR and CRLF normalize to LF. It rejects NUL, every other C0 control including tab, C1 controls, DEL, surrogate code points, embedded BOM, and the supported denylist of bidi controls (`U+061C`, `U+200E/U+200F`, `U+202A-U+202E`, and `U+2066-U+2069`) with a generic field error that does not echo confidential content. Rejected CSV control-character rows remain invalid and do not retain a staged display payload.
- HTML/script-shaped strings and URI-scheme-shaped strings are not rejected merely for containing `<`, `>`, `javascript:`, `data:`, `vbscript:`, or an external URL. They remain literal stored plain text. Existing Django autoescaping and `linebreaksbr` escaping protect CSV preview and Faculty workspace output; generated revision, Question Selection Audit, and Faculty/Admin questionnaire print continue using autoescaped text nodes, while resumable-import JavaScript uses `textContent` and no HTML insertion API. No question-content CSV/XLSX export exists, and this character-policy change requires no schema migration.

### Departmental Exam Builder Automatic Generation dedupe
- Automatic Generation uses the existing normalized `QuestionPayloadService.question_fingerprint()` identity to treat duplicate Submitted rows as one logical question, not as invalid content. Every eligible row in a collision group remains an alternative until the global two-set proof jointly chooses whether to use that logical question and which single representative supplies its campus, difficulty, contributor, and section provenance. This avoids greedy first-row allocation bias while preserving one logical question per normalized fingerprint in each final questionnaire. Manual Generation continues to use its existing raw-row and Stage 6 behavior.
- Aggregate-only readiness and the Automatic Summary disclose `submitted • unique • duplicate copies automatically ignored` counts without question text, answer choices, correct answers, or faculty identities. Duplicates are warning/information only if the deduplicated pool is feasible. If it is infeasible, TMP reports the actual aggregate/difficulty shortage (for example, `Moderate: 22 available / 25 required`) rather than a generic duplicate blocker.
- Automatic selection retains the existing deterministic/HMAC selection and ordering context, adds the `normalized-text-v3` Automatic input policy marker, and defensively rejects a generated Automatic set that repeats a normalized fingerprint. Its bounded proof limit is 1,000,000 states. The logical-assignment fast path supports both disjoint output and mathematically required positive overlap: total, campus, and difficulty logical-group capacities establish the first possible overlap; exact campus-by-difficulty table pairs and shared logical slots prove feasibility at that value; and a shared slot selects one concrete allocation-aware alternative for one appearance in each set. The solver increases overlap only after the lower value has no hard-feasible witness. Contributor balancing remains soft and does not enter this hard-feasibility gate. Manual selection remains bounded at 500,000. The remediation is schema-free and does not introduce Faculty Request to Reopen behavior.
- Automatic flat readiness and output now share `solve_automatic_identity_aware_two_sets()` and obtain its hard-proof `max_states` from `resolve_automatic_generation_max_states()`. That one Automatic-only resolver reads `DEPARTMENTAL_EXAM_GENERATION_MAX_STATES`, defaults to 1,000,000, and is also used for an explicit processing override; the selector itself has no hidden fallback budget. The shared path compresses fixed logical-question campus/difficulty cells, finds a deterministic feasible pair of exact quota tables, and assigns one representative per logical fingerprint using stable HMAC ranks. Readiness gates only hard final-count, campus, difficulty, fingerprint, and minimum-overlap constraints; contributor representation/concentration remains descriptive and cannot cause a feasibility-limit blocker. Manual Review continues to call the generic Stage 6 feasibility and identity-aware advanced selectors with its unchanged limits.

### Faculty Exit Pulse
- `Classroom Tools -> Exit Pulse` is the Phase 1 in-class Learning Check workflow. A faculty user with `exit_pulse.use` may select only their own accepted assignment in the current tenant/campus scope and launch one five-minute session using a lesson topic plus one of three predefined learning questions or a rule-validated custom question. The tenant setting `FEATURE_EXIT_PULSE_ENABLED` controls availability and defaults On for compatibility after deployment.
- Students use a cryptographically random public URL or its dynamically generated QR code without logging in. The bearer token stays in the browser URL fragment, is removed from browser history before a CSRF-protected POST opens the survey, and is never placed in the Nginx/Gunicorn request path. Exit Pulse is confidential, identity-validated classroom feedback: the student must enter a student number that matches an active enrollment in the exact session course offering, tenant, campus, academic year, and term before the response form opens.
- The public survey uses `Referrer-Policy: same-origin` so mobile browsers can send a valid same-origin source on the automatic CSRF-protected form post. The fragment bearer token is not included in request or referrer data, and `Origin: null` remains rejected rather than being trusted.
- The verification page displays privacy notice version `2026-07-identity-v1`. There is no separate checkbox: entering and submitting the student number is the affirmative acknowledgment, and not continuing means not participating. The server stores the notice version and acknowledgment timestamp; it does not trust public notice fields. The student number is not placed in URLs, hidden fields, local storage, public tokens, rendered errors, or ordinary logs.
- Successful verification creates a ten-minute server-side Django session state tied to the exact Exit Pulse session, validated enrollment, browser hash, notice version, and server timestamp. Final submission revalidates lifecycle, assignment scope, tenant/campus, and active enrollment. A database uniqueness constraint permits one response per session/enrollment across browsers; browser and IP controls remain rate-limit defense in depth. Verification failures use one generic message and separate browser/IP limits to reduce enumeration. LocMemCache remains per worker, so production should use an approved shared cache for coordinated throttling.
- Faculty may extend a live session once by five minutes, close it early, or cancel it. Live polling exposes only the total count; written answers remain hidden until the session is closed or expired. Owner-only results contain aggregate counts/rates and enabled confidential text without responder identity. Live, results, dashboard, Class History, and Assignment Comparison receive no student number, student name, or enrollment identity context. Exit Pulse has no responder/nonresponder list, attendance or grading integration, faculty evaluation/ranking, charts, exports, or administrator analytics.
- Technical browser-token hashes expire after about 24 hours. The backward-compatible `anonymize_exit_pulse_identifiers` command clears only those hashes and preserves reactions, optional written responses, and validated-enrollment accountability records. Its legacy name is retained for operational compatibility.
- New responses store an immutable protected relation to the validated enrollment plus notice version and acknowledgment time. Responses created before the migration remain null/blank legacy confidential-unidentified records; TeacherMate+ does not infer or backfill identity from current enrollment. The dedicated `exit_pulse.response_identity_investigate` permission is created without any default role grant, and no identity-reveal interface exists. Any future one-response investigation workflow requires approved roles, scope, reason, immutable auditing, and retention governance.
- Exit Pulse Phase 2 Checkpoint 1 adds backend analytics only. When a draft transitions to `LIVE`, TeacherMate+ stores `enrollment_count_snapshot` using the same active-record plus `ACTIVE` enrollment rule used by Phase 1; the locked start transition writes it once, zero is valid, and later roster changes do not replace it. Existing sessions remain null because current enrollment must not be misrepresented as historical enrollment.
- For a legacy null snapshot, the Phase 1 single-session result service may still show the current eligible enrollment count as an explicitly identified estimate. Weighted assignment response analytics exclude legacy sessions from both the response numerator and enrollment denominator and report their count separately. Weighted response rate is `responses from terminal sessions with stored snapshots / sum of those snapshots`; weighted understanding and support-needed rates use their respective valid response counts over all valid responses from `CLOSED` and `EXPIRED` sessions. Draft, live, and cancelled sessions are excluded and all divisions are zero-safe.
- Exit Pulse Phase 2 Checkpoint 2 adds a faculty-only dashboard and Class History. The dashboard supports academic-year/term filtering, current sessions, ten recent terminal sessions, assignment history, and neutral weighted summary cards. Class History is terminal-only, supports date, question-type, normalized topic, and closed/expired status filters, and paginates 20 sessions per page while preserving filters. List pages never display written-feedback content or responder identity.
- Dashboard and history authorization starts from the authenticated faculty owner plus current tenant/campus scope. A Class History URL uses the UUID of one owned session as an opaque assignment-history reference; the server resolves it back to that same owner and scope before loading any assignment records. The original faculty owner keeps read-only history after an assignment is deactivated or replaced but cannot create from it, and replacement faculty do not inherit the prior owner's sessions. Stored zero enrollment remains valid, legacy null is shown as unavailable/not historically comparable, and response rates above 100% remain visible because eligible enrollment can change after the immutable start-time snapshot.
- The Phase 2 post-implementation review makes faculty Exit Pulse fail closed when no active tenant/campus scope is available, keeps dashboard/history routes GET-only, normalizes distinct topic counts with database-side trimming while excluding whitespace-only values, and makes the legacy single-session fallback explicit in the result UI: the displayed current eligible class count and derived response rate are estimates, not historical enrollment facts.
- Exit Pulse Phase 2 Checkpoint 3 adds the read-only faculty Assignment Comparison page. Its candidates are the exact owner's current eligible assignments plus that owner's historical assignments only when matching terminal data exists in the active tenant/campus scope. Academic-year, term, and question-type filters apply server-side to both the five summary cards and assignment rows; the stable assignment table paginates 20 rows and links to the latest completed result and owned Class History.
- Assignment Comparison includes only `CLOSED` and `EXPIRED` sessions. Weighted response rate uses responses and summed enrollment snapshots only from terminal sessions with a non-null historical snapshot; a stored zero remains real and distinct from a legacy null, null-only rows are marked not historically comparable, and rates over 100% remain uncapped with neutral wording. Understanding and support-needed rates use all valid responses in the filtered terminal scope, distinct topics are database-trimmed, and the latest terminal record is selected deterministically by `started_at` then record ID. The page never loads or displays written feedback and remains exact-owner, permission, feature, tenant, and campus scoped. Charts, exports, faculty rankings/evaluation, administrator analytics, schema changes, and public-workflow changes remain out of scope.

- Organization: tenants, campuses, departments, programs
- NCBA organizational structure for actual-data setup:
  - NCBA has two broad branches of operation: Academic and Administrative. TeacherMate+ grading governance currently models the Academic side directly; Administrative units may be represented later only if they need grading, approval, reporting, or account-governance scope.
  - The Academic branch has three broad departments: Graduate, College, and Basic Education.
  - College is subdivided for governance and data ownership into Business Administration (BA), Information System and Computer Science (IS/CS), Liberal Arts (LA), and Accountancy.
  - The Academic branch is headed by the Chief Academic Officer (CAO).
  - Business Administration has a College Dean covering the three campuses.
  - Academic Chairmen are campus-scoped by college area: BA, Accountancy, LA, and IS/CS. Cubao currently has no BA Academic Chairman.
  - Basic Education is managed by a Principal per campus, with Academic Coordinators per campus.
  - Basic Education is subdivided into Elementary, Junior High School, and Senior High School.
  - For setup discipline, courses, sections, course offerings, students, faculty assignments, grading templates/profiles, and governance roles should be mapped to the most specific department/area that owns the data. This improves filtering, RBAC scope, monitoring, correction routing, and grade-distribution governance.
  - Departments now support a parent-child hierarchy plus Academic/Administrative branch and Division/Area/Office classification. Use parent Division records such as College, Basic Education, and Graduate Studies when users need broad filters or broad governance scope, then create child Area records such as BA, IS/CS, LA, Accountancy, Elementary, JHS, and SHS.
  - Department-scoped roles assigned to a parent department include active child departments in Admin Portal scope. This allows a Dean, Principal, or similar broad academic reviewer to cover all child areas without duplicating every child assignment.
  - Hierarchy coverage is parent-to-child only: a parent division can cover child areas, but a child-area assignment does not cover its parent or sibling areas.
  - Inactive records are visible only on their own maintenance pages for review/reactivation. Dependent operational scopes, Faculty Portal class access, SIS grade export, deadline reminders, non-compliance notice targeting, template hotfix candidates, and grading/reporting reads require an active tenant/campus/academic-year/term/department/program/course/section chain. For example, an inactive department is managed on the Departments page, but its programs, courses, sections, offerings, students, and grading outputs are excluded from operational lists and processing.

## 4. Grading Model (Current Behavior)
- Supports hierarchical grading structures:
  - Level 1: period components (e.g., Exam, Class Standing)
  - Level 2: subcomponents (e.g., Quizzes, Participation/Output)
  - Level 3: detail items (optional)
- Attendance is template-driven, not globally hardwired:
  - attendance contributes to grading only when a template subcomponent is explicitly marked as `is_attendance_component`
  - the attendance-marked subcomponent still uses the template's normal weight hierarchy, so attendance can carry its own weight through subcomponent and component percentages
  - attendance is treated as part of `class_standing_grade` when it sits under a non-`EXAM` component
  - attendance is not automatically a universal Class Standing item for every template
- Attendance scoring currently uses this internal mapping before roll-up:
  - `PRESENT = 100`
  - `EXCUSED = 100`
  - `LATE = 90`
  - `ABSENT = 0`
  - the student attendance score for the period is the rounded average of the active attendance-session records found for that attendance-marked subcomponent path
- Attendance computation example:
  - if a student has 4 attendance records in the same grading period with statuses `PRESENT`, `PRESENT`, `LATE`, and `ABSENT`, TeacherMate+ converts them to `100`, `100`, `90`, and `0`
  - attendance average = `(100 + 100 + 90 + 0) / 4 = 72.50`
  - if that attendance subcomponent has a weight of `10%` inside a `Class Standing` component, then its weighted contribution is applied through the normal template roll-up together with the other subcomponents of that component
  - if the `Class Standing` component itself has a weight of `60%` in the period, the final attendance effect on the period grade is still governed by both layers of weight, not by attendance alone
- Supports score entry methods:
  - raw score (computed against total/base)
  - direct percentage items (configured behavior)
- Summary page computes and presents period results and readiness indicators.
- Passing threshold policy now supports layered resolution:
  - profile-level (`TenantGradingProfile.passing_grade_threshold`)
  - assigned grading-template level (`GradingTemplate.passing_grade_threshold`)
  - tenant-level system setting (`PASSING_GRADE_THRESHOLD`)
  - fallback default `75.00`
- Final-grade computation policy now supports layered resolution too:
  - profile-level final-grade formula via `TenantGradingProfile.final_grade_formula_mode`
  - fallback default of averaging all active grading periods in the assigned template
  - weighted formulas treat missing configured periods as `0` until an official period grade is available, so later periods still affect the final result through their configured weight
  - prediction services now follow the same resolved tenant final-grade strategy for:
    - projected final grade
    - average still needed across remaining periods to finish with a passing final grade
  - the admin template-testing calculator previews the selected template and applies an active Tenant Grading Profile assigned to that template when one exists; it still does not simulate full offering-specific scope such as campus, department, program, course, or term-type matching

- Enrollment CSV preview resolves tenant, campus, academic year, term, course, student, and offering references through request-local caches and loads the authorized offering lookup once per batch. Confirmation revalidates all staged offering IDs against current tenant/campus/department and active-record scope, preloads referenced students and existing enrollment pairs, and retains per-row transactions, audit records, duplicate protection, and error reporting.
- The Enrollment Adjustments page now renders inside the standard Admin Portal shell again, so the left navigation and top bar remain visible instead of making the page feel standalone.
- Faculty Portal now has `Attendance Summary` at `/faculty/my-courses/<offering_id>/periods/<period_id>/attendance/summary/`. It is read-only, shows student attendance from the start of class to the current date, filters by All/Warning/Exceeded Limit, sorts the most at-risk students first, and flags students who hit three consecutive absences.
- The tool does not decide whether the correction is academically valid. It only protects records and audits the authorized adjustment.
- The adjustment only changes enrollment rows:
  - creates the destination `Enrollment`
  - deactivates the source `Enrollment`
  - preserves all source offering gradebook, attendance, submission, correction, reopen, and lock records
  - does not create, edit, delete, submit, unlock, recompute, or migrate grade records
- Impact analysis is per selected student and counts attendance records, source offering activities, activity scores, submissions, period grades, final grades, correction requests, reopen requests, and locked periods. The page labels which counts are student-specific and which are source-offering-wide.
- Classification rules:
  - `SAFE`: no academic records exist for the source offering/student impact.
  - `WARNING`: academic records exist, including any existing final-grade record that is not submitted. Processing requires explicit confirmation and logs `completed_with_warning`.
  - `BLOCKED`: source and destination are the same, a destination enrollment already exists, a final grade is already submitted, a course-offering period is locked, or a matching campus-level grading period lock is active.
- Each processed or blocked row writes `EnrollmentAdjustmentLog` with student, source/destination offering, source/destination enrollment IDs where available, source previous active/status values, destination active/status values, batch reference, reason, processor, processed time, result, warning flags, and the impact snapshot.
- Permissions:
  - `enrollment_adjustment.view` allows the page, impact analysis, history, and audit details.
  - `enrollment_adjustment.process` allows actual processing. Default process grants are limited to Superadmin, Tenant Admin, Campus Admin, and Registrar. Area Chair, Dean, College Dean, and CAO are view-only by default unless Superadmin explicitly grants processing permission.
- Known limitation: when moving across campuses/programs, the destination enrollment stores the destination offering scope, but the student's master record is not automatically rewritten. Student master-data corrections should still come from the proper SIS/import workflow when Pinnacle changes the student's campus, department, or program.
