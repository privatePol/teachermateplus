# Faculty login control

Gate 2 implementation, 2026-11-07. No activation, installation, publication or normal-database migration is included.

## Policy and lifecycle

- `FEATURE_CLEARANCE_LOGIN_DISABLE_ENABLED` is a tenant-only SystemSetting BOOL, default **OFF**, configurable under Automatic Faculty Login Disabling in Admin Portal > Configurable Features (Configuration Management). `CLEARANCE_LOGIN_DISABLE_DELAY_DAYS` stores whole days as INT, minimum **1**, default **2**. The form and policy service validate server-side. Global settings never activate or change this tenant policy. No migration seeds it ON.
- The Faculty Portal records an event only after a CLEARED official clearance PDF has been built successfully and its download audit recorded. This is successful **server-side PDF generation**, not receipt or physical printing. Preview GETs, incomplete clearance and renderer exceptions create no deadline. Upgrade migration 0015 records each existing report cycle as historically uncertain without asserting that PDF generation succeeded. A first post-upgrade reprint of such a cycle is terminal EXEMPT while ON, with MIS audit; while OFF it is terminal CANCELED. Fresh cycles retain first-successful-PDF behavior.
- One unique cycle is `(faculty user, tenant, campus, term)`. Its first successful generation timestamp, saved `delay_days`, and deadline (`timestamp + days * 24 elapsed hours`, computed in UTC) remain fixed. Changing configured days affects new events only. Repeated generation, including after cancellation, manual override or MIS exception, never rearms that cycle. Report references include a random suffix so concurrent regenerations do not collide at second precision; term text in the reference is capped to keep the existing 64-character field bound.
- Times are aware; deadline display is explicitly Asia/Manila. The command applies due deadlines and authentication/request middleware enforces the cutoff even if cron is late. This path can make scoped account/audit writes on a request when a deadline becomes due.
- Another active role, administrative access, or active/open loading outside the cleared campus/term creates a terminal `EXEMPT` event with a `CLEARANCE_LOGIN_EXCEPTION` audit record for MIS. Loading/role checks run at generation and again at application. Same-campus loading in the next term (or any other still-active/open term) is a continuing obligation; only the cleared campus/term is excluded. The check is deliberately conservative: operations must close/unassign active loading, rather than relying on an elapsed term calendar date. Exceptions are not automatically retried after MIS changes loading; manual login control remains available.
- Saving OFF atomically changes every PENDING event in the selected tenant to terminal CANCELED with actor/time/reason and per-event audit, without restoring disabled login or changing applied events. Re-enabling cannot revive canceled events. Successful PDFs first generated while OFF store a terminal CANCELED cycle marker with generation metadata, not a pending action; later reprints cannot arm that cycle. New qualifying cycles while ON may schedule normally. Manual Enable/Disable Login remains available whether the policy is ON or OFF.

## Manual control and access

- Security > Users shows login status separately from Active/Inactive and puts the login action beside existing icons. The modal requires explicit confirmation; the endpoint accepts only CSRF-protected POST with an explicit operation and expected version. A stale/no-longer-applicable request returns HTTP 409.
- Permission: `users.login_access.update`, seeded additively for existing SUPER_ADMIN/CAMPUS_ADMIN roles. The baseline initializer also grants it when those roles are created after migrations on a fresh database. No SUPERADMIN alias is supported: repository role definitions and writers use SUPER_ADMIN. No existing custom permission/deny rows are overwritten. Scoped operators need a single fully covered tenant/campus target and a campus-level management grant. Department-only role grants do not confer this account-wide power. Multi-scope, global, staff or administrative targets require a different superuser. Self and superuser targets are protected. Direct DENY wins, including against a superuser.
- `login_disabled` is independent of `is_active`. Ordinary User saves, account ModelForms and inherited password forms exclude login_disabled/login_access_version from their UPDATE columns and reload the current values afterward; both fields are non-editable model fields. Stale edits cannot reset login state or decrease the revocation version. Enable Login does not activate an inactive user, create an account, change a password, grant roles or bypass OTP, permission checks, correction approvals or grade locks.
- Manual enable increments a persistent session version and permanently marks all existing PENDING/APPLIED deadlines OVERRIDDEN across the account. Unique terminal cycle rows prevent old-event regeneration from scheduling again. A new qualifying term/campus cycle can create a new deadline.
- Both manual changes revoke registered sessions and advance the session authentication hash, including Django secret-key fallback hashes. Version zero preserves existing session compatibility; a revoked old/unregistered/rotated session cannot return after enabling. Password authentication, OTP completion and Django Admin honor the independent state. Legacy ModelBackend remains registered to read old sessions; the first backend raises PermissionDenied to stop authentication fallback for denied users. Request middleware guards old sessions and handles exact cutoff logout.
- Exception-affecting Role/Permission/UserRole/UserPermission and FacultyAssignment/CourseOffering model and queryset writes share account locks with the worker (including bulk activation and update_or_create). Existing-target role assignment locks actor/target in ID order before reading/reactivating the grant. Full faculty provisioning locks its administrator at the start of its transaction, before duplicate checks, account creation and audit insertion. Its newly inserted target is already exclusively owned by that transaction; the shared internal assignment body retains role/permission/scope checks without a second actor lock or assignment-service transaction. Replacement, import and initializer writers take their account locks before existing assignment/offering locks. If activation commits first, processing observes the exception; if disabling commits first, later provisioning does not silently enable login. MIS must use independent Manual Enable Login. SQLite uses a no-op version write to acquire its writer lock without advancing the version; complete provisioning units use bounded retries only outside an existing outer transaction. Real MariaDB/InnoDB multi-process acceptance remains a release gate.

## Transactions and scheduling

- Administrative acceptance locks only its actor and faculty participating in the selected tenant/year/term, in account ID order; it then locks the tenant, academic scope, assignments and authorization rows. Every acceptance row lock uses NOWAIT on MariaDB/MySQL. Attendance cutoff publication can retain its campus mutex/source order: acceptance never waits while holding a conflicting account or scope lock. A busy lock rolls back the complete acceptance unit and triggers bounded retries only at a root transaction; nested callers receive a reload/retry error without replaying their outer work. SQLite retains its complete-unit writer retry. No tenant-wide attendance mutex or global account-domain lock is added by acceptance. Newly discovered unlocked participants are rejected; current authorization, candidate hash, ownership, count and audit checks remain intact.
- MariaDB/MySQL acceptance requires NOWAIT support and Django's READ COMMITTED isolation. Unsupported/REPEATABLE READ configurations fail closed before acceptance row locking; this avoids validating an old discovery snapshot. Confirm actual deployed settings and execute both commit orders with same-tenant and cross-tenant shared users on a disposable InnoDB database before staging acceptance. Registry reconciliation retains its persisted account/password/version checks.

- Manual changes, generation and application serialize on the user row. Successful PDF construction, download audit and cycle recording share one transaction and user/tenant locks, so policy changes serialize with generation. Account locks are acquired in ID order before tenant policy and event locks. Manual control includes actor/target; policy OFF locks its actor before tenant/events, preventing audit foreign-key lock inversions. Shared catalogue changes lock the account domain first; metadata-only explicit saves avoid this when exception fields are absent. This is conservative serialization and can add contention to catalogue edits. Conditional user-version updates and a unique cycle constraint defend stale work. SQLite lock failures retry only the complete rolled-back unit with bounded backoff; failures inside an existing outer transaction propagate to its owner.
- State/version updates, registered-session deletion and audit writes commit together. A failed audit rolls them back; retries produce one terminal transition. Sessions already executing cannot be recalled; denial applies on subsequent requests.
- Prepared command: `python manage.py process_clearance_login_deadlines --limit 100`; `--dry-run` reports without mutation. The cron template includes a once-per-minute `flock` entry. It is **not installed by this implementation**. Feature OFF remains independent of cron installation.
- Migrations: `accounts.0012_faculty_login_control` adds two user fields and the event table with cycle uniqueness, deadline check and due/user indexes; `accounts.0013_clearance_login_policy` adds `delay_days` (default 2), a database minimum-1 constraint and CANCELED choice without changing existing deadlines; `accounts.0014_protect_login_control_fields` marks the independently managed user fields non-editable (state-only on SQLite, no value rewrite); integration migration `rbac.0037_seed_login_access_permission` follows staging's RBAC 0036 and grants the dedicated permission to established SUPER_ADMIN/CAMPUS_ADMIN roles. The feature-branch seed was named 0034; target migration ledgers have not been inspected. Confirm it has never been applied in a target before deploying this renamed migration; otherwise design an additive reconciliation. No grading, attendance, contribution or historical-data rewrite. Accounts 0015 creates the historical cycle marker table and captures existing clearance-report scopes conservatively, without changing reports or user access. Historical PDF success is not inferred. No retroactive deadline migration.

- Follow [the historical-clearance cutover procedure](FACULTY_LOGIN_CONTROL_CUTOVER.md) only under a later authorized deployment gate. Closing admission, draining and stopping every legacy clearance writer before the snapshot is mandatory; migration code cannot stop an old process. Keep the policy OFF through initial staging tests. Snapshot re-scanning is idempotent and conservatively excludes uncertain history.
