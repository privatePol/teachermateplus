# Historical clearance cutover

This is a procedure for a later, separately authorized deployment. None of these operational steps was executed in the local remediation gate. The default and initial staging policy remains OFF.

## Release prerequisites

Verify the exact approved application artifact and actual deployed Django migration ledger, including accounts 0012-0015 and staging RBAC 0034-0037. If the feature branch's original RBAC 0034 was applied anywhere, stop and design additive ledger reconciliation; do not rename an applied migration. Verify a restorable database backup and record baseline report counts, scoped cycle counts, login-disabled/version values and pending/terminal deadline counts. Confirm MariaDB/InnoDB, NOWAIT capability and READ COMMITTED for the application connection. Independently review the code and run actual shared-user transaction tests before release.

## Controlled sequence

1. Verify Automatic Faculty Login Disabling is OFF for every affected tenant. On a pre-feature release, verify the setting is absent (the new code's default is OFF); where a compatible policy workflow already exists, use it to save OFF and cancel pending events. If an existing ON policy cannot safely be turned OFF with compatible code, STOP and prepare that operation separately. Do not enable a worker against missing schema. Do not change login-disabled state or revocation versions to prepare the release.
2. Close admission to legacy clearance creation on every application node and direct upstream endpoint. Include the Faculty Portal clearance POST, direct calls to `FacultyFinalClearanceReportService.generate_report_record`, management/shell scripts and any scheduled/background writers. A load-balancer route block alone does not drain in-flight requests or stop internal writers.
3. Drain existing requests and transactions, then stop or otherwise fence every old writer. The operator must verify that no legacy process can create a clearance record and that no in-flight legacy transaction remains. Keep this fence in place through migration and compatible application startup. If writer quiescence cannot be verified, STOP before the snapshot.
4. Under the later migration authorization, apply the approved graph including accounts 0015. The migration records each distinct `(faculty, tenant, campus, term)` already represented by a report. It does not infer that creation proves successful rendering or physical printing; incomplete/failed/unknown historical outcomes are conservatively excluded from automatic disabling. It does not modify reports, account access, session versions, existing deadlines or grades.
5. Before lifting the fence, verify there is no existing report scope missing a HistoricalClearanceCycle marker, confirm distinct scoped marker counts against the frozen source, and compare baseline report/account/deadline values. The data function supports safe repeat scans of the same quiescent source; do not fake or reapply a recorded migration. Any catch-up scan after an interrupted release needs its own reviewed operational authorization.
6. Deploy/start only the compatible application on every node while the legacy-writer fence remains closed. Verify all old processes are gone, schema and artifact identities match, policies remain OFF, and the new PDF path always records terminal OFF markers after successful generation. If mixed old/new writers remain, STOP; do not resume clearance writes.
7. Resume clearance operations with the compatible version only. Verify historical reprints do not schedule disabling, a successful new cycle while OFF records CANCELED, re-enabling does not revive it, existing manual overrides persist, and preview/failed rendering creates no pending action. Verify authentication, scope, audit, manual control and scheduler behavior under the separate staging acceptance plan. Policy activation requires its own authorization.

A report created by an old process after the snapshot would defeat historical protection if its cycle had no marker. The stop/drain/fence sequence prevents that gap; neither a Python migration nor a unit test is an application-process fence. Tests cover the drained in-flight writer boundary, upgrade, idempotent scans and historical reprints, not actual deployment control.

## Interruption and rollback

If the snapshot or verification fails, keep clearance admission closed and the automatic policy OFF. MySQL DDL may not roll back atomically: inspect schema and ledger before recovery, retain the backup, and use a reviewed recovery plan. Do not assume replaying a partially applied migration is safe.

Prefer rollback to a schema-compatible application that continues enforcing login-disabled state and session versions. An old pre-feature binary can ignore restrictions even though the additive schema remains present; do not resume authenticated traffic on it without a reviewed enforcement plan. Keep history markers and terminal deadlines; dropping them can rearm old cycles. Do not blanket-enable accounts, reset versions, erase audits or unapply migrations as a rollback shortcut. Code rollback, schema recovery and any backup restore are separate authorized operations.
