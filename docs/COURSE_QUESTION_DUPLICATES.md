# Course examination duplicate contract

Version: `course-question-v3` (supersedes the unshipped v1/v2 contracts). Scope: authoritative primary CycleCourse, including its existing equivalent members, inside one tenant/cycle. Other cycles are independent. No historical-reuse workflow is included.

## Faculty procedure

1. Add/edit a question before the contribution deadline. Exact normalization uses NFC and collapses whitespace, preserving case and mathematical characters: `x²` is not `x2`. The stem and choice multiset normally determine duplication, preserving multiplicity. When the stem or choices suggest labels or positions (such as “Both A and B,” “All of the above,” “First and third,” or numeric ordinals such as “1st and 3rd”), identity conservatively retains ordered choices. This intentionally favors extra similarity warnings over false rejection for ambiguous wording; it is not a natural-language meaning classifier. Answer and difficulty never bypass identity. Stored choices are never reordered. Rejection retains entered and saved content. Existing stem-similarity normalization/warnings remain separate and advisory.
2. Upload CSV or Word and correct all malformed rows. Word supports staged correction; CSV errors require re-upload. Confirmation decides each row once as accepted or duplicate-skipped. Only accepted candidates consume quota. If they exceed capacity, reduce the file: nothing is imported. Example: 45/50 plus seven rows containing two exact duplicates accepts five and finishes at 50/50.
3. Resume an interrupted import. Processed-row progress includes skipped rows; accepted/skipped totals describe the reserved plan. Questions remain unpublished until every row is processed. Replays keep the same decisions even when the competing question is later removed.
4. Build Cases incrementally. Narrative identity ignores presentational styling, uses NFC text, and preserves case, symbols, table nesting/row/cell boundaries, spans, ordered-list starts, list order and superscript/subscript structure. Member identity combines narrative and question identity; bundle identity adds encoded member order. Changing a narrative or member rechecks all identities in the same transaction. Conflicts preserve the whole saved Case and entered form; no member is silently trimmed.

## Administrator procedure and legacy gate

1. After schema deployment is separately authorized, run the read-only command on explicitly authorized data: `python manage.py duplicate_question_preflight --tenant-id ID --cycle-course-id ID --limit 20000`. It outputs version, primary/member IDs, counts, and collision question/batch/row IDs only. It neither acquires claims nor changes content. Exceeding the bound or invalid structure fails without partial conclusions. This session does not run this command against staging.
2. Review any actual collisions before enabling affected writers. The schema migration adds an empty reservation table and an empty JSON import-plan field. It does not choose owners, delete questions or backfill Submitted/history records. Initialization inventories the unit under the existing cycle lock; reconciliation changes only missing, changed or obsolete claims and retains identical claim IDs. Existing pool conflicts receive distinct content-safe guidance to contact the exam coordinator, not a misleading request to rewrite the user's new question. Resolution requires an explicit decision about identified records. Do not edit Submitted records to make migration succeed.
3. Complete old active imports before upgrading. An unfinished legacy import without recorded decisions, or one whose decisions use a different identity version, cannot resume: it follows terminal cleanup of unpublished rows and requires re-upload. Existing confirmed imports/history remain intact. No additional schema migration is needed: each row decision in the existing JSON field persists `identity_version`, alongside `identity` and `disposition`. Every decision must declare the same supported current version, including skipped and processed rows. Missing, incompatible and mixed versions fail closed before initialization, acquisition or transfer. Stored pending digests are never assigned a replacement version. Empty never-planned previews with no committed rows may start a fresh plan. Rollback to older code loses the duplicate contract and cannot safely resume new imports; finish active work and retain migration/data backups before any separately authorized rollback.

4. Admin Scenario create/edit/membership replacement/deletion reconciles resulting member, narrative and standalone identities in the same transaction. A collision rolls back the complete overlay mutation, including linked order and audit writes; source Submitted questions are not rewritten. Existing authorization, Closed/pre-lock requirements, and Faculty-owned Case restrictions remain unchanged.

## Reservations and generation

If another writer encounters an incompatible pending plan during pool initialization, their mutation rolls back and the offending upload is left for its owner; no faculty identity or content is disclosed. The owner's retry records FAILED and cleans only that upload's unpublished questions/claims. Repeated cleanup/retry is idempotent. Confirmed imports bypass pending-plan validation and their published questions/claims are not purged. A rejected other-owner import initialization stays READY with no new decisions or claims. For example, Red/Blue/Green/“1st and 3rd” is not equivalent after swapping Blue and Green; Red/Blue/Green/Yellow still matches after that swap. Numeric ordinal detection covers case, parenthesized/slash-separated, spaced/hyphenated/dotted and superscript suffix variants; ambiguous cases conservatively retain order.

All normal writers retain the existing cycle-first transaction lock and database uniqueness. Reservations are uniquely constrained by primary course/version/digest; ownership is either an accepted Question or an accepted pending import row. The first chunk initializes the existing pool, fixes decisions and acquires pending claims. Each chunk transfers only its accepted rows' claims in place; later chunks do not scan the pool or delete/recreate reservations. Claim writes scale with accepted chunk size, not pool size. Questions remain unpublished until confirmation. Deleting a Draft removes its claim; metadata/narrative edits exchange affected claims atomically. Submitted protections remain intact. Terminal or abandoned cleanup deletes only that batch's unpublished rows and pending claims, without pool reconciliation, so unrelated legacy collisions cannot prevent FAILED status. Confirmed/Submitted questions and their claims are protected; confirmed shell cleanup also preserves Question-owned claims. Active jobs become abandoned after 24 hours without progress, rechecked under lock. A preview's 30-minute expiry does not expire an active job.

Automatic SUFFICIENT_POOL excludes Blocked Draft content from reservations, matching generation's exclusion. Content remains stored. Roster reactivation before the deadline reacquires all claims atomically or rolls back. An authorized reopened Draft may remain Blocked; Final Submission must acquire its identities when it becomes Submitted. Strict/Manual retain their Draft reservations and existing policy gates.

Automatic generation/readiness use the same logical identity and retain allocation alternatives for legacy duplicates, whole Cases, encoded order, exact quotas and historical snapshot evidence. Narrative identity results and validation failures are cached within each assessment. Malformed relevant Cases are excluded whole with content-safe reasons; irrelevant Draft narratives/members are not assessed as Submitted inputs. Hard shortages and allocation constraints still block generation. Manual generation fails closed on legacy logical collisions. Input fingerprints carry the new identity version; historical normalized-text-v3, course-question-v1 and course-question-v2 audit snapshots continue using their recorded identities. Rich-content and set-integrity digests are separate and unchanged. Duplicate-free accepted counts do not guarantee section/campus/whole-Case feasibility.

Focused SQLite tests prove functional transactions only. Disposable MariaDB/InnoDB two-connection tests and authenticated browser acceptance remain separate validation gates.
